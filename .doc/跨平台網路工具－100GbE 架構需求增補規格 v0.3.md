# 跨平台網路工具
## 100GbE Architecture Requirement Amendment

版本：0.3 Draft  
基礎規格：SRS v0.1 + System Design v0.2

---

# 104. 必要需求升級

以下三項正式由「建議功能」升級為：

```text
MUST
Mandatory Requirement
```

不得延後至第二階段。

---

# 104.1 M-01 Safe Apply / Automatic Rollback

任何可能造成網路中斷的設定變更，都必須支援：

```text
Snapshot
↓
Validate
↓
Apply
↓
Verify
↓
Confirmation Window
↓
Commit
```

未收到確認：

```text
Timeout
↓
Automatic Rollback
↓
Verify Original State
```

包括：

```text
IPv4
IPv6
Gateway
DNS
Route
MTU
VLAN
```

其中 VLAN / Route 若尚未納入第一版功能，未來加入時同樣必須遵守此規則。

Rollback Timer 必須由：

```text
Privileged Helper
```

管理。

不得由：

```text
GUI
CLI process
```

管理。

因此即使：

```text
GUI crash
CLI killed
Frontend disconnected
```

Rollback 仍必須執行。

CLI：

```bash
nettool profile apply lab \
  --confirm-timeout 30
```

確認：

```bash
nettool profile confirm
```

立即復原：

```bash
nettool profile rollback
```

---

# 104.2 M-02 Node Control Plane / Data Plane 分離

Node Protocol 必須拆成：

```text
Control Plane
+
Data Plane
```

Control Plane 僅負責：

```text
Authentication
Pairing
Capability Negotiation
Test Creation
Test Configuration
Start
Stop
Statistics
Error
Health Check
```

不得承載大量測速 Payload。

真正的 100GbE 測速：

```text
TCP Data Plane
UDP Data Plane
Accelerated Data Plane
```

必須與 Control Plane 分離。

架構：

```text
Node A                         Node B

Control ──────────────────── Control
          TLS/Auth

TCP #1  ==================== TCP #1
TCP #2  ==================== TCP #2
TCP #3  ==================== TCP #3
TCP #N  ==================== TCP #N

UDP     ~~~~~~~~~~~~~~~~~~~~ UDP
```

---

# 104.3 M-03 Loss / Drop 必須分類

系統禁止將所有：

```text
missing packet
```

統稱為：

```text
Packet Loss
```

至少必須區分：

```text
Network Packet Loss

Capture Drop

Analyzer Drop

Application Drop

Unknown / Indeterminate
```

例如：

```text
Network Loss:
0.013%

Capture Drop:
0.002%

Analyzer Drop:
0%

Application Drop:
0%
```

如果 Capture 層本身發生 Drop：

```text
Capture Drop > 0
```

則 TCP Retransmission、Out-of-order、Packet Loss 等被動分析結果必須降低可信度。

GUI 必須明確標示：

```text
Analysis Confidence
```

例如：

```text
HIGH
MEDIUM
LOW
```

並提供降低可信度的原因。

# 105. 100GbE 正式列為核心效能需求

原本：

```text
10 GbE Primary Target
25 GbE Stretch Target
```

修改為：

```text
1 GbE      Compatibility Baseline
10 GbE     Mandatory
25 GbE     Mandatory
40 GbE     Mandatory
100 GbE    Primary Performance Target
```

也就是系統架構必須以：

```text
100 Gigabit Ethernet
```

環境為設計上限之一。

不得先以 1G/10G 架構完成後，再假設單純增加執行緒即可支援 100G。

---

# 106. 100G 必須拆成三種能力

「支援 100G」禁止作為單一驗收條件。

必須拆成：

## 106.1 100G Throughput Generation

產生接近 100GbE 能力的 TCP / UDP 流量。

---

## 106.2 100G Real-time Analysis

在 100GbE 流量環境下即時：

```text
Packet Count
Byte Count
Flow Count
Protocol Statistics
TCP Statistics
Drop Statistics
Top Talkers
```

---

## 106.3 100G Full Packet Capture

完整保存：

```text
Packet Header
+
Packet Payload
```

至 PCAP / PCAPNG。

這三個工作負載必須獨立測試。

原因：

```text
Throughput Generator
≠
Real-time Analyzer
≠
Full Packet Recorder
```

三者的 CPU、PCIe、Memory 與 Storage I/O 模型完全不同。

---

# 107. 100GbE Data Rate

100Gbps 理論資料率：

```text
100,000,000,000 bit/sec

÷ 8

= 12.5 GB/sec
```

因此如果完整保存原始資料：

```text
1 second
≈ 12.5 GB

1 minute
≈ 750 GB

10 minutes
≈ 7.5 TB
```

以上尚未加入：

```text
PCAP metadata
Filesystem overhead
Index
Analysis metadata
```

因此：

> 100G 即時封包分析列為核心必要能力，但「100G 無遺失完整 PCAP 長時間錄製」不得直接視為一般工作站的必要能力。

Full Capture 必須另外建立：

```text
Certified Capture Hardware Profile
```

才能宣告：

```text
Lossless 100G Capture
```

---

# 108. Small Packet Worst Case

100GbE 不只需要看：

```text
Gbps
```

還必須看：

```text
Mpps
```

以 64-byte Ethernet Frame 並計入 Ethernet wire overhead：

```text
Preamble / SFD
Inter-frame Gap
```

理論線速約為：

```text
148.8 Mpps
```

因此 Packet Engine 的主要壓力測試必須包含：

```text
64-byte packets
```

而不能只拿：

```text
1500-byte
9000-byte
```

封包測試。

---

# 109. 正式 Benchmark Frame Size

至少測試：

```text
64
128
256
512
1024
1518
9000
```

位元組級距。

其中：

```text
64 byte
```

用於 Packet Rate Worst Case。

```text
1518 byte
```

代表一般 Ethernet Frame。

```text
9000 byte
```

用於 Jumbo Frame 環境。

# 110. Packet Engine 架構升級

原架構：

```text
NIC
↓
Capture
↓
Ring Buffer
↓
Analyzer
```

升級為：

```text
                     NIC
                      │
              Hardware RSS
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   RX Queue 0      RX Queue 1     RX Queue N
       │              │              │
       ▼              ▼              ▼
   Worker 0        Worker 1       Worker N
       │              │              │
       └───────┬──────┴───────┬──────┘
               │              │
               ▼              ▼
          Flow Shards     Counters
               │
               ▼
          Aggregator
               │
        ┌──────┴──────┐
        ▼             ▼
      GUI          Exporter
```

Linux networking stack 本身也提供 RSS、RPS、RFS、XPS 等平行化機制，證明高速資料路徑不能只依靠單一 RX/TX 執行緒。

# 111. 禁止 Per-Packet Allocation

100G Mode 中：

```text
malloc()
new
Vec::new()
String allocation
JSON serialization
```

不得存在於正常 per-packet hot path。

必須使用：

```text
Preallocated Memory

Memory Pool

Fixed-size Descriptor

Batch Processing

Reusable Buffer
```

概念：

```text
RX Descriptor
      │
      ▼
Preallocated Buffer
      │
      ▼
Parser
      │
      ▼
Flow Counter
```

---

# 112. Batch Processing

禁止：

```text
receive packet
process
receive packet
process
```

作為唯一高速模式。

應採：

```text
RX Burst
   │
   ▼
Packet Batch
   │
   ▼
Parse Batch
   │
   ▼
Update Counters
```

例如：

```text
32
64
128
256
```

個封包一批。

實際最佳 Batch Size 必須由 Benchmark 決定，不得硬編碼成單一數字。

---

# 113. Multi-Queue

100G NIC 必須支援利用：

```text
RSS
RX Queue
TX Queue
```

將不同 Flow 分散至多個 CPU Core。

DPDK Poll Mode Driver 直接操作 RX/TX descriptors 並以 polling 模式處理高速封包，是其高效能模型的核心。

---

# 114. CPU Affinity

100G Mode 必須支援：

```text
CPU Pinning
```

例如：

```text
RXQ0 → CPU 4

RXQ1 → CPU 5

RXQ2 → CPU 6

RXQ3 → CPU 7
```

禁止讓 OS Scheduler 任意頻繁搬移高速 Packet Worker。

---

# 115. NUMA Awareness

100G Server 常見多 CPU Socket 環境，因此系統必須取得：

```text
NIC NUMA Node

CPU NUMA Node

Memory NUMA Node
```

並優先：

```text
NIC
  │
same NUMA
  │
CPU
  │
Memory
```

避免：

```text
NIC NUMA 0
     │
     ▼
CPU NUMA 1
     │
     ▼
Memory NUMA 0
```

產生跨 NUMA 記憶體流量。

DPDK 的高效能指南亦要求考量 Huge Page 與 NUMA locality。

# 118. AF_XDP 與 DPDK 不應互相取代

兩者用途不同。

## AF_XDP

適合：

```text
原本 NIC 仍由 Linux 使用

需要高速 Packet Processing

不希望整張 NIC 完全退出 Linux network stack
```

---

## DPDK

適合：

```text
Dedicated Test Port

Dedicated Capture Port

Maximum Packet Rate

Controlled Benchmark Environment
```

因此產品必須保留兩種模式。


# 120. Windows 100G Engine

Windows 分成：

```text
Standard Socket Engine

High Performance Socket Engine

DPDK Engine
```

---

# 120.1 Standard

```text
Winsock
+
IOCP
```

提供一般相容性。

---

# 120.2 High Performance

評估並實作：

```text
Winsock Registered I/O
RIO
```

Microsoft 將 RIO 定位為降低網路延遲、提高訊息率，以及改善高效能網路應用 I/O 效率的 Winsock extension。

RIO Buffer 必須：

```text
Pre-register
Reuse
```

不得反覆 Register / Deregister。

Microsoft 文件明確指出重複進行 buffer registration / deregistration 會造成顯著效能下降。

---

# 120.3 Windows DPDK Mode

對符合硬體矩陣的 NIC，可提供：

```text
DPDK Accelerated Mode
```

例如 DPDK ICE PMD 官方文件涵蓋 Intel Ethernet 800 Series：

```text
10
25
50
100 Gbps
```

並提供 Windows prerequisites；Windows 下需使用 NetUIO 存取支援的 Intel Ethernet hardware。

因此 Windows 100G 必須採：

```text
Certified NIC Matrix
```

不能宣稱：

```text
Any Windows 100G NIC
```

皆可使用 DPDK 模式。

# 131. 100G Packet Engine 必須避免 Global Lock

禁止：

```text
RX Worker
   │
   ▼
Global Mutex
   │
   ▼
Flow Table
```

應使用：

```text
Flow Sharding
```

例如：

```text
RSS Hash

% worker_count
```

決定：

```text
Flow Shard
```

使同一 Flow 儘量由同一 Worker 處理。

# 137. Backpressure

```text

```

```text

```

```text

 ├── Analyzer
 │
 ├── Statistics

 └── Capture Writer
```

```text

```

不得拖慢整個 Analyzer。

# 149. 架構決策結論

在 100GbE 條件下，本專案不再只是：

```text
Cross-platform network utility
```

而是：

```text
Cross-platform Control Plane

        +

Platform-specific
High-performance Data Plane
```

最終設計原則：

> GUI、CLI、Network Profile 與 Node 控制維持高度跨平台；100GbE 高效能資料路徑則依 Windows、Linux、macOS 能力選擇不同 Backend，不以「所有平台必須使用完全相同底層技術」為目標。

如此才能同時滿足：

```text
Windows

macOS Intel

macOS Apple Silicon

Linux KDE

          +

100GbE
```

而不犧牲核心效能。
