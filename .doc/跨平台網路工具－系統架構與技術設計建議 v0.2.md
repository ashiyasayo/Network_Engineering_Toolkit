# 37. 技術選型結論

本專案建議採以下架構：

```text
Language:
Rust

GUI:
Tauri 2
+ TypeScript
+ React 或 Svelte

CLI:
Rust
+ clap

Async Runtime:
Tokio

Local Data:
SQLite

Config Import / Export:
YAML
JSON

Packet Capture:
Provider abstraction

Windows:
Npcap

macOS:
libpcap / BPF

Linux MVP:
libpcap

Linux Performance Mode:
AF_PACKET / TPACKET_V3

Node Control Plane:
Authenticated encrypted control connection

Node Data Plane:
Raw TCP
Raw UDP

Privileged Operations:
Dedicated privileged helper
```

Rust 適合此專案主要不是因為 GUI，而是 Core、CLI、Node、Socket I/O 與封包處理均需要較低執行成本與良好的記憶體安全性。Rust 官方將效能與無 GC runtime 列為其核心特性，而 Tokio 提供 TCP、UDP、非同步 I/O、排程及多執行緒 runtime。

Tauri 2 可使用相同桌面程式碼支援 Windows、macOS 與 Linux，因此適合將 GUI 保持為較薄的一層。

# 40. GUI 技術選擇

## 建議方案：Tauri 2

優點：

- GUI 與 Rust Core 整合容易。
- Core 不需要轉成另外一個 Service。
- CLI 與 GUI 可共用 Rust crate。
- UI 與高速 data plane 完全分離。
- Windows、macOS、Linux 可使用同一 GUI 架構。

缺點：

- Linux GUI 仍有桌面環境相關相依性。
- macOS 特殊系統權限仍需 native helper。
- 網路封包大量資料不得直接透過 frontend event 傳送。

因此：

```text
Packet
  ↓
Rust Analyzer
  ↓
Aggregator
  ↓
Statistics Snapshot
  ↓
Tauri IPC
  ↓
GUI
```

禁止：

```text
Packet
  ↓
Tauri Event
  ↓
JavaScript
```

逐封包傳送。

# 41. 其他 GUI 方案

## 方案 B：C# + Avalonia

Avalonia 官方目前支援 Windows、macOS Intel、macOS Apple Silicon，以及 Linux X11 / Wayland；亦支援 Native AOT。

### 優點

- C# 開發效率高。
- XAML 適合複雜桌面 GUI。
- Windows 開發體驗佳。
- 跨平台 UI 成熟。

### 缺點

高效封包處理仍需要：

```text
P/Invoke
native wrapper
或
Rust/C library
```

如果最後變成：

```text
C# GUI
+
Rust Packet Engine
+
Rust Speed Engine
```

則語言與 FFI 邊界會增加。

### 建議

如果團隊 C# 能力遠高於 Rust，可以考慮。

否則本專案仍建議：

```text
Rust Core
+
Tauri
```

---

## 方案 C：C++ + Qt

Qt 6.11 官方支援 Windows、macOS x86_64 / ARM64，以及多個 Linux 平台。

優點：

- Native 桌面工具經驗成熟。
- Linux/KDE 整合自然。
- 高效能。
- 系統 API 整合容易。

缺點：

- C++ 開發及維護成本較高。
- Memory safety 成本較高。
- Build system 與跨平台 packaging 較複雜。
- Qt 授權策略需於產品化前確認。

### 結論

如果是企業級純桌面產品：

```text
Qt
```

是很強的方案。

如果同時重視：

```text
CLI
Node
Packet Engine
Speed Engine
```

我會優先選 Rust。

# 43. Windows Adapter

優先使用 Windows 系統 API。

Windows IP Helper API 可取得 Adapter、IP、route、TCP/UDP endpoint，亦提供新增與修改單播 IP 位址的 API。

DNS 則已有：

```text
GetInterfaceDnsSettings
SetInterfaceDnsSettings
```

API。

但需注意：

`CreateUnicastIpAddressEntry()` 建立的位址並非持久設定，Adapter 重設或重新開機後可能消失。

因此 Windows Adapter 需另外處理：

```text
Runtime IP state

vs.

Persistent adapter configuration
```

不能直接把兩者視為同一件事。

---

## Windows 建議策略

MVP 可使用官方 Windows 網路管理能力完成持久設定，例如 Windows PowerShell 的：

```powershell
New-NetIPAddress
Set-NetIPInterface
Set-DnsClientServerAddress
```

Microsoft 官方文件亦以這些 Cmdlet 進行 Static IP、Gateway、DNS 與 DHCP 設定。

但正式版本建議逐步將高頻操作改為直接 native API。

也就是：

```text
MVP
PowerShell / Native API hybrid

V1
Native API first
```

# 44. macOS Adapter

macOS 不建議大量呼叫：



因此建議：


# 46. Privileged Helper

這是整個系統非常重要的設計。

禁止：

```text
sudo nettool-gui
```

禁止：

```text
Run GUI as Administrator
```

建議：

```text
GUI / CLI
    │
Local Authenticated IPC
    │
    ▼
nettool-helper
    │
    ▼
Operating System
```

Helper 只暴露極少數 API：

```text
GetNetworkState

ApplyNetworkProfile

RestoreNetworkState

WriteHosts

StartCapture

StopCapture
```

不要提供：

```text
ExecuteArbitraryCommand(string command)
```

否則 Helper 本身會成為極大的 privilege escalation surface。

---

# 47. macOS Privilege

macOS 建議使用 Apple：

```text
SMAppService
```

管理 helper / daemon。

Apple 說明 macOS 13 之後可透過 SMAppService 註冊 Login Item、LaunchAgent 或 LaunchDaemon。

macOS Helper 可以考慮使用：

```text
Swift
+
SMAppService
+
XPC
```

即使主程式是 Rust，也不必強迫所有程式碼都是 Rust。

建議：

```text
Rust Core

Swift Privileged Helper
```

反而會使 Apple 平台權限模型較清楚。

# 54. Hosts 管理策略

# 63. Latency

預設不要使用 One-Way Latency。

原因：

```text
Node A clock
≠
Node B clock
```

若沒有可信的時鐘同步，One-Way Latency 不可靠。

因此預設：

```text
RTT
```

使用：

```text
Ping
Pong
```

計算。

未來若偵測：

```text
PTP
或其他可信時間同步
```

才提供 One-Way Latency。

# 71. Flow Key

```text

```

```text
Five Tuple
```


# 72. TCP Retransmission

TCP Retransmission 分析需要追蹤：

```text
Sequence Number
ACK
Window
Flow Direction
```

結果應分類：

```text
Observed Retransmission

Suspected Retransmission

Out-of-order
```

不要把：

```text
Sequence gap
```

直接全部視為：

```text
Packet Loss
```

因為被動 capture 本身也可能遺失封包。

# 73. Capture Drop 必須獨立呈現

Packet Dashboard 至少要分：

```text

AB42-E991-...
```

使用者確認後保存 trust relationship。
